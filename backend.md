# Abhyas — backend & moderation plan

**Author:** Claude · **Status:** proposal for adversarial review
**Purpose:** hand this to a second reviewer to attack. Section 11 lists the
weaknesses I already know about — attacking those is more useful than
attacking the parts I'm confident in.

---

## 1. What this system is

A course-resource archive for IIT Hyderabad. Students arrive knowing a course
code, and leave with a past paper, notes, an assignment, or a textbook.

Current state: a **static site** — plain HTML/CSS/JS, no build step, no
server code. Six pages, one stylesheet, a `RESOURCES` array in `data.js` that
is currently placeholder data. There are no real PDFs yet.

## 2. Constraints, in priority order

These are ranked deliberately. Where they conflict, the higher one wins.

1. **Succession.** The owner graduates. Whoever inherits this must be able to
   run it without being a developer, and nothing may be tied to a personal
   account. *This outranks performance and cost.*
2. **Moderation.** Nothing a student uploads may become public before a human
   has opened the file and confirmed it is what it claims to be.
3. **Simplicity of the daily task.** "Upload, fill in details, it's live."
4. **Speed.** The site should feel instant. It currently does.
5. **Cost.** Student project. Should run on hosting already paid for.

## 3. Architecture in one paragraph

Three separable layers. **Bytes** (PDFs) live on the hosting filesystem.
**Metadata** lives in one JSON file. **The site** is static and does all
filtering in the browser. A small PHP layer exists for exactly two jobs:
accepting uploads and letting the admin approve them. Nothing else is
server-rendered.

## 4. Directory layout

The single most important detail in this document:

```
/home/uXXXXX/
├── abhyas-pending/          ← NOT reachable from the web
│   ├── 9f2a1c4e8b3d7a05.pdf
│   └── 9f2a1c4e8b3d7a05.json     (sidecar: submitted metadata)
├── abhyas-private/          ← NOT reachable from the web
│   ├── config.php               (password hash, paths, limits)
│   ├── backups/                 (rolling copies of resources.json)
│   └── rejected/                (optional retention)
└── public_html/
    ├── files/                   ← approved PDFs only
    │   └── CS/CS2110/CS2110-endsem-2024.pdf
    ├── resources.json           ← the live index
    ├── courses.json             ← code → name registry
    ├── contributors.json        ← contributor registry
    ├── admin/                   ← review console
    └── index.html, styles.css, …
```

**Why pending files sit outside `public_html`:** anything under the web root
is on the public internet the instant it is written — before review, and
executable if someone disguises a script as a PDF. Moderating a file that is
already publicly fetchable is not moderation. The admin previews pending
files through a PHP script that checks the session first.

**Why a sidecar JSON per submission** rather than one `pending.json`: two
students uploading at the same moment cannot corrupt each other. The queue
is concurrency-safe by construction, with no locking.

## 5. File naming

```
files/{DEPT}/{CODE}/{CODE}-{examType}-{year}[-{n}].pdf
files/CS/CS2110/CS2110-endsem-2024.pdf
```

- The folder tree is browsable without a database. If every JSON file were
  lost, the archive would still be navigable by hand.
- A takedown is deleting one file plus one record.
- The filename is **generated by the server from the approved metadata**,
  never taken from the uploader.

**Records store the path relative to `files/`** — `"CS/CS2110/CS2110-endsem-2024.pdf"`
— not a full URL. Moving the files later (subdomain, CDN, new host) is then
one constant in the code instead of editing every record.

## 6. Data model

### 6.1 `resources.json` — the live index

```json
{
  "id": "cs2110-2024-endsem",
  "title": "Algorithms — End-Sem Paper",
  "code": "CS2110",
  "course": "Design and Analysis of Algorithms",
  "department": "CS",
  "semester": 4,
  "type": "papers",
  "examType": "End-Sem",
  "professor": "—",
  "year": 2024,
  "file": "CS/CS2110/CS2110-endsem-2024.pdf",
  "pages": 6,
  "sha256": "…",
  "contributor": "c1",
  "added": "2026-08-23"
}
```

`type` is one of `papers | notes | assignment | reference` and drives the
colour system across the whole site. `contributor` is an **id**, not a name
— see 6.3.

### 6.2 `courses.json` — the course registry

```json
"CS2110": {
  "name": "Design and Analysis of Algorithms",
  "sem": 4,
  "professors": [],
  "branches": ["CS"]
}
```

Typing a code in the admin form fills in the name, semester and suggested
professors. This kills the drift already visible in the current data, where
`MA1210` is recorded once as `"Rajesh Kannan, Sukumar"` and once as
`"Sukumar, Rajesh Kannan"` — the same two people, two spellings.

**Critical subtlety:** the registry must **not** hard-set `department`.

In this archive `department` means *"which branch's students take this"*, not
*"which department teaches it"* — it drives the branch filter pills and the
Bookshelf shelves. The existing data proves one code maps to different
branches:

| Code | Department in the live data |
|---|---|
| `MA1010` Elementary Linear Algebra | **CS** |
| `MA1110` Calculus-I | **CS** |
| `MA1310` Differential Equations | **MSME** |
| `CY1120` Materials Chemistry | **MSME** |
| `CY2140` Environmental Chemistry | **CM** |

A fixed `code → department` map would move a CS student's linear algebra
paper into Maths, and they would stop seeing it under their own branch.
`branches` is therefore a **suggestion list** that pre-selects the dropdown;
the admin confirms it per submission.

### 6.3 `contributors.json` — the contributor registry

```json
"c1": { "name": "Aarav Menon", "roll": "CS23" }
```

Resources reference `"contributor": "c1"`. **Names are never copied into
resource records.** If the name were stored inline, "Aarav Menon" and
"aarav menon " become two people and the leaderboard splits their points —
exactly the drift the course registry exists to prevent. The admin form
autocompletes against existing contributors and only creates a new id when
there genuinely is a new person.

`roll` is the **branch+year token only** (`CS23`), never a full roll number.
The site is public and a full roll number identifies one student.

`"contributor": null` means shared without credit — counted in the archive,
absent from the leaderboard. Credit is opt-in, so the board inherits that.

## 7. The pipeline

```
Student uploads (public form)
        │
        ▼
  submit.php  ── validates ──► abhyas-pending/<id>.pdf + <id>.json
        │                       (outside web root — not public)
        ▼
  Admin logs in → review console
        │
        ├── previews the PDF (streamed through session check)
        ├── corrects the metadata (registry auto-fills)
        │
        ├─ Approve ─► move file into public_html/files/{DEPT}/{CODE}/
        │             append record to resources.json (atomically)
        │             delete pending sidecar
        │
        └─ Reject ──► move to abhyas-private/rejected/, log reason
```

**Approval is edit-then-approve, not just approve.** Students will pick the
wrong course code and leave the name blank. If approval were all-or-nothing,
good papers would get rejected over bad metadata. Every field is editable in
the review screen, with the registry filling in as the code is corrected.

**Honor Roll points need no separate mechanism.** Points are computed from
`resources.json` at render time, so approving a file grants its points and a
takedown removes them. That is deliberate: the Terms page promises a file can
be withdrawn on request, and a board still paying out for a withdrawn file
would quietly break that promise.

**Duplicate detection:** `sha256` is computed at upload. If it matches an
existing record, the console flags it before the admin approves.

## 8. Security requirements

The public upload endpoint is unauthenticated and writes files to a server.
This is the highest-risk component in the system and the part most worth
attacking.

### 8.1 Upload (`submit.php`)

- Enforce a max size **server-side** (client limits are advisory only).
- Verify the file **actually is a PDF** by reading its magic bytes (`%PDF-`),
  not by trusting the extension or the browser-supplied MIME type.
- **Never** use the uploaded filename. Generate one:
  `bin2hex(random_bytes(8))`.
- Write only into `abhyas-pending/`, outside the web root.
- Rate-limit per IP, and cap the total pending queue size, or the queue is
  trivially floodable by one script.
- Return a generic error on failure — no paths, no PHP messages.

### 8.2 Admin authentication

- `password_hash()` / `password_verify()`; the hash lives in
  `abhyas-private/config.php`, outside the web root. **No plaintext password
  anywhere in the repo.**
- `session_regenerate_id(true)` on successful login.
- Cookie flags: `HttpOnly`, `Secure`, `SameSite=Lax`.
- **Every API action re-checks the session server-side.** The JavaScript that
  hides the console is a convenience, not a security boundary.
- Throttle failed logins.
- `.htaccess` Basic Auth over `/admin/` as a second, independent layer.

### 8.3 Serving pending files

- The `id` parameter must be validated against `^[a-f0-9]{16}$` **before** it
  touches the filesystem. This is the path-traversal guard and it is not
  optional.
- Check the session, then `readfile()` with `Content-Type: application/pdf`,
  `X-Content-Type-Options: nosniff`, `Content-Disposition: inline`.

### 8.4 Writing `resources.json`

The whole site reads this one file. A half-written copy blanks Archive,
Bookshelf and the Honor Roll simultaneously.

- `flock()` exclusive for the read-modify-write.
- Write to a temp file, `json_decode()` it to prove it parses, then
  `rename()` over the original — `rename()` is atomic on the same filesystem.
- Keep the last N copies in `abhyas-private/backups/`.

### 8.5 Defence in depth

- `.htaccess` in `files/` disabling PHP execution, so even a bad file that
  somehow lands there cannot run.
- `admin/` and both private directories excluded from git.

## 9. Viewing PDFs

**Public site:** Adobe PDF Embed API. It is a *viewer* — it renders a file
you host, it does not store anything. Keep the PDFs on the **same domain** as
the site or the browser blocks the viewer from reading them.

It must be isolated behind one function, for two reasons: its client ID is
tied to an Adobe account and a registered domain (a succession liability),
and that isolation makes PDF.js a drop-in replacement if that ever bites.

**Admin console:** a plain `<iframe>` and the browser's own PDF viewer. The
console is desktop-only and private, so the mobile-rendering problems that
rule out iframes on the public site do not apply. This avoids handing session
-protected bytes to a third-party viewer.

## 10. Filtering and search

**Stays entirely client-side. No query API.**

`resources.json` is fetched once; every filter, sort and search after that is
instant, works offline, and costs nothing per query. At a few thousand
records this is roughly 1 MB of JSON, ~150 KB gzipped — a single request.

This also means the entire existing front-end keeps working unchanged.
`fetchResources()` in `data.js` is already the single seam; it becomes a
`fetch()` of `resources.json` and nothing else in the app is touched.

**Revisit at roughly 10,000 records**, or if per-user state is ever needed.

## 11. Known weaknesses — attack these first

I would rather these be argued about than defended.

1. **`resources.json` is a single point of failure.** Atomic writes and
   backups reduce the risk; they do not eliminate it. Is a file-per-resource
   directory with a build step better, despite being more moving parts?
2. **Every visitor downloads the entire index**, including records they will
   never look at. At what record count does this actually become the wrong
   design — and is splitting it later a painful migration?
3. **Contributor identity is admin-assigned, with no accounts.** Someone can
   claim to be someone else, and the admin cannot really verify it. Does a
   leaderboard without authenticated identity invite abuse worth designing
   against, or is social pressure at a small campus enough?
4. **Rate limiting by IP is weak** — campus NAT means many students share an
   address, so limits are either too loose to stop a flood or tight enough to
   block legitimate users. Is a captcha worth the friction on a page whose
   whole job is lowering friction?
5. **No malware scanning.** A PDF that is structurally valid can still be
   malicious. Shared hosting rarely offers scanning. Accepted risk?
6. **PHP on shared hosting** is a maintenance surface: version upgrades,
   disabled functions, host-specific behaviour. Every line of it is a line
   the successor may have to debug.
7. **No audit log** of who approved what and when. With one admin this is
   fine. With three it is not.
8. **Rejected-file retention** has a privacy dimension — how long may we keep
   something we refused, and does the uploader get told?
9. **The Adobe dependency** is an account that must be inherited.
10. **PHP could be avoided entirely** by having the admin upload by FTP and
    edit JSON through a local form-based tool. That is more manual work per
    file but removes the entire attack surface in section 8. I chose against
    it because it fails constraint 3 — is that the right trade?

## 12. Deliberately rejected, with reasons

Attack the reasoning, not the conclusion.

- **WordPress as the backend** — its media library is the same hosting
  filesystem with a database in front. For a site that is not
  WordPress-rendered, that is ceremony plus a security-patching burden.
- **Cloudflare R2 / object storage** — technically better on egress cost, but
  adds an account to inherit. Under constraint 1, that loses. Revisit only if
  bandwidth actually becomes a problem.
- **Server-side filtering / a query API** — slower and costlier than
  client-side at this scale, and it would mean rewriting a front-end that
  already works.
- **Storing computed totals** (points, counts) — must be derived, or a
  takedown leaves stale points behind.
- **A single `pending.json`** — concurrent submissions corrupt it.
- **`code → department` as one-to-one** — breaks the branch filter (see 6.2).
- **Contributor names inline in records** — splits leaderboard identity.

## 13. Build order

Each phase leaves the site working.

1. **`resources.json` + fetch swap.** Move metadata out of `data.js`; point
   `fetchResources()` at the JSON. No server code. Immediately reduces the
   "one comma breaks everything" risk.
2. **Real files + the public viewer.** Upload a handful of PDFs by hand under
   `files/`, add the `file` field. `resource.html` (the per-file page) is
   already built and reads `files/{r.file}` directly — it just needs real
   PDFs at those paths to stop showing "preview not available yet". It
   currently renders with a plain `<iframe>`, not the Adobe viewer this
   line originally called for: Adobe needs a credential nobody has set up
   (see HANDOVER.md §2), and a same-origin iframe already does live PDF
   rendering in every evergreen browser with zero new account. Swap it for
   Adobe later if its extra chrome (page thumbnails, in-viewer annotation)
   turns out to matter — that's a one-function change in `resource.js`.
3. **The review console against real data**, admin-only, no public uploads
   yet — the admin adds resources through it.
4. **Public submissions.** `submit.php` plus all of section 8. This is the
   phase that introduces real risk and should be reviewed hardest.
5. **Housekeeping.** Backups, audit log, rate limiting, retention policy.

Phases 1–3 are useful even if 4 is never built.

## 14. Questions I most want a second opinion on

1. Is a single `resources.json` the right call, or file-per-resource?
2. Is public upload worth the attack surface, versus the admin filing things
   people email in? (The archive is currently email-only and works.)
3. Is Adobe the right viewer given it is an inheritable account, or is
   self-hosted PDF.js the better long-term answer?
4. Does the phased order leave any phase where the site is broken or
   half-migrated?
5. Anything in section 8 that is missing, wrong, or cargo-culted?

### 3. Attack on Section 11 ("Known Weaknesses") & Critical Flaws

1. **Weakness 4: Campus NAT completely breaks IP Rate Limiting (Severe failure)**
   - *Failure scenario:* 5,000 students at IIT Hyderabad connect through campus Wi-Fi (`eduroam` / hostel LAN) sharing 1 to 2 public outbound NAT IPv4 addresses. An IP rate-limit of 5 uploads/hour means that as soon as one student uploads 5 papers during exam week, **the entire campus gets HTTP 429 blocked**. Conversely, an attacker switching cellular IPs can flood the queue unimpeded.
2. **Weakness 9: The Adobe Dependency directly violates Constraint 1 (Succession)**
   - *Failure scenario:* Adobe PDF Embed API requires an active Adobe Developer Console account bound to the domain (`iith.online`). When the current maintainer graduates, that Adobe account expires or gets orphaned. A non-technical successor will see a blank box with `Invalid Client ID / Domain Mismatch` on every single resource page. 
3. **Weakness 6 & 10: The Public Upload Attack Surface vs. Email/Drive Intake**
   - *Failure scenario:* A public unauthenticated PHP upload endpoint on shared hosting invites automated scrapers and bots uploading multi-gigabyte files, exhausting Hostinger's strictly enforced **inode limit** and disk quota, resulting in Hostinger freezing the account.
4. **Weakness 1: Single `resources.json` + Manual Cache-Busting Conflict**
   - *Failure scenario:* `HANDOVER.md:34-36` states that cache-busting on the site is manual (`?v=N`). If `resources.json` is updated dynamically by PHP when an admin approves a file, returning students whose browsers cached `resources.json` with standard `Cache-Control` headers will **not see the newly approved resources** unless cache headers are strictly managed.

### 5. Ranked Objections

#### 🔴 BLOCKERS (Must be changed before building)

1. **BLOCKER 1: The Adobe PDF Embed API Dependency violates Constraint 1 (Succession)**
   - *Consequence:* Hard external account dependency that breaks all PDF rendering when credentials lapse or domain changes.
   - *Fix:* Replace Adobe with a lightweight, self-hosted **PDF.js** viewer embedded inside the existing modal system. Zero accounts required.

2. **BLOCKER 2: Storing `abhyas-pending/` outside `public_html/` breaks Hostinger Git Deployment and Successor Backups**
   - *Consequence:* Hostinger's native Git Auto-Deployment and cPanel/hPanel file managers operate strictly within `public_html/` or domain roots. Files outside `public_html` are excluded from standard web backups, causing successors to lose unreviewed submissions during server migrations.
   - *Fix:* Keep storage inside a secured folder under root: `public_html/.storage/pending/` and `public_html/.storage/private/` with an `.htaccess` containing `Require all denied` and `php_flag engine off`. This keeps the entire repository and data self-contained in one tree while remaining 100% inaccessible to public HTTP requests.

3. **BLOCKER 3: Schema breaks `books.js` & Reference Books**
   - *Consequence:* `resources.json` omitting the `book: { author, publisher, cover, gist }` payload breaks the BookShelf component on `library.html` with JavaScript exceptions.
   - *Fix:* Explicitly support optional `book` metadata for `type === "reference"` in the `resources.json` schema and admin moderation forms.

---

#### 🟡 SHOULD-FIX (Will cause operational bugs if ignored)

4. **SHOULD-FIX 1: Campus NAT breaks IP Rate Limiting**
   - *Consequence:* Legitimate students on campus Wi-Fi blocked by global IP throttling.
   - *Fix:* Use an in-memory or cookie-based submission token combined with a global hourly queue cap (e.g. maximum 50 pending submissions system-wide) rather than per-IP blocking, plus client-side Turnstile/reCAPTCHA or proof-of-work if bot spam occurs.

5. **SHOULD-FIX 2: Browser Caching of `resources.json`**
   - *Consequence:* Newly approved resources do not appear for students due to aggressive browser caching.
   - *Fix:* Ensure the frontend fetches `resources.json?t=` or `.htaccess` sends `Cache-Control: no-cache, must-revalidate` for `resources.json`.

6. **SHOULD-FIX 3: Non-Technical Admin Password Reset**
   - *Consequence:* A successor who forgets the password cannot generate a bcrypt hash via PHP CLI.
   - *Fix:* Provide an emergency password reset script (`admin/reset.php`) that only functions if a physical file `reset.flag` is created via Hostinger File Manager.

---

#### 🟢 NITPICK (Minor improvements)

7. **NITPICK 1: No automatic backup pruning in `backups/`**
   - *Fix:* Ensure `upload.php` keeps only the last 20 rolling copies of `resources.json` to prevent inode bloat.

### 6. Direct Answers to the 5 Questions in Section 14

1. **Is a single `resources.json` the right call, or file-per-resource?**
   - **Single `resources.json` is the right call.** A file-per-resource directory requires a build step (Node/SSG/CI), violating the core project constraint ("no build step, plain static site"). At 1,000 resources, `resources.json` is ~150KB (uncompressed), which loads in <30ms over 4G.
2. **Is public upload worth the attack surface, versus the admin filing things people email in?**
   - **Admin-only review & publishing with public staged submissions is worth it, IF public intake is constrained.** Direct student uploads drastically increase contribution volume compared to email. Because uploads land in a quarantined folder as randomized `.tmp` files with `%PDF-` magic-byte verification and `.htaccess` execution disabled, the attack surface is completely neutralized.
3. **Is Adobe the right viewer, or is self-hosted PDF.js the better long-term answer?**
   - **Self-hosted PDF.js is the better answer.** Adobe violates Constraint 1 (Succession) by binding the site to an external Adobe Developer account and domain whitelist. PDF.js is 100% account-free and self-contained.
4. **Does the phased order leave any phase where the site is broken or half-migrated?**
   - **No, but Phase 1 must include the `book` schema update** so that `library.html` does not crash when reading from `resources.json`.
5. **Anything in section 8 that is missing, wrong, or cargo-culted?**
   - Missing: **Direct HTTP caching header rules** for `resources.json` to prevent stale client caches.
   - Wrong: **Strict IP rate-limiting** which fails under campus-wide NAT.

### 7. Concrete Alternative Architecture: The Hardened Self-Contained Model

```
public_html/
├── .storage/                      ← Protected by .htaccess (Require all denied)
│   ├── pending/                   ← Staged uploads (9f2a1c4e.pdf + .json)
│   ├── private/
│   │   ├── config.php             (Admin password hash)
│   │   └── backups/               (Last 20 copies of resources.json)
│   └── .htaccess                  (php_flag engine off, Deny from all)
├── files/                         ← Public approved PDFs
│   ├── .htaccess                  (php_flag engine off, execution disabled)
│   └── CS/CS2110/CS2110-endsem-2024.pdf
├── api/
│   ├── submit.php                 (Public upload endpoint → .storage/pending/)
│   └── moderate.php               (Authenticated review actions)
├── assets/
│   └── pdfjs/                     (Self-hosted PDF.js viewer — 0 external accounts)
├── admin/                         (Authenticated review console)
├── resources.json                 (Live index)
├── courses.json                   (Course registry)
├── contributors.json              (Contributor registry)
└── index.html, library.html, etc.
```

This ensures 100% Git compatibility, zero external vendor account dependencies, full protection against script execution, and seamless handover for future student maintainers.

### 3. Disputed — BLOCKER 2

The narrow disagreement: **only `pending/` and `private/` need to be outside
the web root.** Approved `files/` must live inside it. So this is about the
quarantine directory alone.

**(a) Fail-safe versus fail-open.** Outside the web root, protection is
*structural* — the server has no route to those bytes. Inside it, protection
is *policy* — one `.htaccess` file. The failure modes are not symmetric:

- Outside, misconfigured → the app breaks loudly. You find out immediately.
- Inside, `.htaccess` lost or ignored → every unreviewed upload becomes
  publicly listable, **silently**. Nobody finds out.

For a directory holding unreviewed files from the public, fail-open is the
wrong default.

**(b) `.htaccess` contradicts the plan's own portability claim.** §1 sells
"redeploy anywhere — GitHub Pages, Netlify, another host." **nginx ignores
`.htaccess` entirely.** The moment a successor migrates hosting — precisely
the Constraint 1 scenario — `.storage/` becomes a public directory with no
error. Your Constraint-1 fix introduces a Constraint-1 failure.

Also: `php_flag engine off` is unreliable under PHP-FPM/LSAPI, where it is
ignored or throws a 500. On LiteSpeed you generally need `RemoveHandler` /
`AddType`. Worth verifying before relying on it.

**(c) Deploy direction.** You argue outside-webroot breaks Git deploy. I'd
argue the reverse is the real hazard: user uploads living *inside* the deploy
target can be wiped or conflicted by a deployment. Uploads should never sit in
a directory a deploy process manages.

**(d) "100% Git compatibility" is not a benefit here.** Uploads must never be
committed. `terms.html` promises takedown on request — a PDF committed to Git
survives deletion in history, so the promise silently breaks. Keeping uploads
out of Git is a *requirement*, not a limitation to engineer around.

**(e) The backup claim is verifiable and neither of us should assert it.**
Hostinger account backups generally cover the home directory, not only
`public_html`. That is checkable in hPanel in two minutes and should be
checked. Regardless, §4 and `HANDOVER.md` already require a deliberate backup
of the archive that does not depend on the host's default — because the host's
default is not a backup strategy for the one irreplaceable asset.

*Position:* keep `pending/` and `private/` outside the web root. If
verification shows Hostinger genuinely excludes them from backups, the
mitigation is an explicit backup routine — not relocating unreviewed public
uploads into the web root.

### 4. Challenges to your answers

**Q2 — "the attack surface is completely neutralized."** Overstated, and the
word is load-bearing in a way that will cost someone later. Magic-byte
verification proves a file *starts* like a PDF; it says nothing about
embedded JavaScript, malformed structures targeting reader bugs, or what a
student's own machine does on open. Disk and inode exhaustion also survive it
entirely — which your own SHOULD-FIX 1 depends on. "Substantially reduced"
is defensible; "neutralized" invites the next maintainer to stop adding
defences.

**SHOULD-FIX 1 — Turnstile/reCAPTCHA cuts against your own blocker.** Both
require an external vendor account bound to a domain — the exact structure you
correctly rejected Adobe for. If Adobe fails Constraint 1, so does Turnstile.
The account-free half of your fix — cookie-scoped submission token plus a
global pending-queue cap — is the part that survives its own test, and it is
sufficient. Adopt that; leave the captcha as a break-glass option documented
as an account dependency.

Your NAT analysis is right on severity. For the record it was §11.4 in the
original — the value you added is the concrete fix, not the discovery.
